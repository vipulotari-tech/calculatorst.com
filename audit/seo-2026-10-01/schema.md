## Findings and safe changes

### P1/P2: duplicate deck/fence category routes

The baseline build generates `/construction/deck-fence/`, `/construction/decking/` and `/construction/fencing/` with the same 15 tools, identical H1/title/description and separate self-canonicals. Production already redirects the aliases, so this is generated-output residue, not a proven live duplicate-canonical blocker. The two aliases add no distinct intent. Consolidate to the established deck-fence hub using permanent redirects, remove aliases from static paths/sitemap and keep normal link targets canonical. Do not delete any calculators. Reported to root for architecture ownership.

### P2: truncated programmatic metadata

30 descriptions generated by `getCalculatorContent()` are chopped at a character threshold and suffixed with ellipsis. Priority Excavation exposes: “Excavation Calculator — calculate in-place bank volume, loose haul volume and bank volume and related estimates from your measurements. US customary &...” This repeats bank-volume terminology and cuts the units statement. Prefer existing accurate per-calculator `calc.description`, or generate complete sentences from the calculator's scope without hardcoded clipping. Title and description character targets are preview heuristics; avoid removing useful supported features solely to meet 160 characters.

### P2: stable website entity — implemented

`src/layouts/Layout.astro` previously assigned current page descriptions to the same `/#website` entity, making its description change from tool to tool. Changed only WebSite.description to a stable site-level factual description. Page-specific WebPage and social descriptions remain unique.

### P2: author identity accuracy — implemented

`src/pages/author/vipul-otari/index.astro` previously marked the site favicon as the Person's image and the project repository as the Person's sameAs. Omitted both; the visible repository reference remains valid as a source/project link. No portrait, personal profile or credential was invented.

### P2: precise local-processing statement — implemented

`src/components/CalculatorLayout.astro` previously claimed “no data is sent to any server” while the shared layout loads Google Analytics. Replaced that phrase with “Calculator inputs are processed locally in your browser.” Calculator privacy claims now describe the actual calculation behavior without making a broader false network assertion.

### P3: heading outline and source precision

Many calculator interfaces use H3 labels immediately after H1, before their H2 article sections. This is an accessibility/outline improvement opportunity, not an indexing blocker. The shared author card says pages have cited sources; page sources exist, but authority alone is insufficient where a source is a broad institution homepage. Cite a formula/product-specific technical document where applicable. Do not invent review credentials to fill the reviewer component.

## Current Google policy verification

Verified on 2026-10-01 against official primary sources:

- https://developers.google.com/search/updates — May 8, 2026 entry states FAQ rich results stop appearing from May 7, 2026; June 15 entry documents FAQ feature documentation removal. The prior FAQ URL now redirects to updates. Existing factual FAQPage is harmless useful semantic markup; there is no current Google FAQ rich-result gain. Do not convert publisher FAQ into QAPage (that requires genuine user-answer format).
- https://developers.google.com/search/docs/appearance/structured-data/software-app — required properties include name, offers.price and a genuine aggregateRating or review. Current calculator schemas satisfy general Schema.org software semantics but do not qualify for Google's software rich-result display because truthful reviews/ratings are absent. This is not an indexing defect, and fabricated ratings must not be added. ReviewedBy is not a substitute for review.
- BreadcrumbList semantics: final breadcrumb can omit item URL; the current final nonlinked calculator breadcrumb is not itself an error. Visible and schema breadcrumb lists come from the same items source.

Useful markup is already rendered in initial HTML. Adding more schema types alone would not resolve low search traffic. Google-selected canonical, coverage status, manual actions, keyword impressions, click history and CrUX are not inferable from these files and require authorized Search Console/field data.
